# Database design

PostgreSQL. Nineteen tables. Verified against a real server, not SQLite —
the constraints that matter most here are ones SQLite does not implement.

## Three rules

**Finalized returns are immutable.** A submitted version is never updated.
Corrections create a new version and mark the old one `SUPERSEDED`. This is
what makes it possible to answer "what exactly did we transmit in April" a year
later.

**Nothing legally required cascades away.** Deleting a user must not delete
their filed returns, payments, or the audit record of what happened to them.
Retention obligations outlive an account deletion request, so those
relationships use `RESTRICT`, and deletion is a status change plus data
minimisation.

**Sensitive columns hold ciphertext.** A read replica, a SQL injection or a
restored backup yields ciphertext for identifiers and bank details.

## Tables

### Identity
| Table | Purpose |
| --- | --- |
| `users` | Credentials, MFA, lifecycle. `status` constrained to four values. |
| `sessions` | One row per session, so revocation is possible. Stores an IP *hash*, never an address. |
| `admin_users` | Staff, with `role` constrained to the six defined roles. |

### Taxpayer and returns
| Table | Purpose |
| --- | --- |
| `taxpayers` | Profile. `ssn_encrypted` plus `ssn_last_four` in the clear for masking. |
| `tax_returns` | One per user per year; unique constraint enforces it. |
| `tax_return_versions` | Immutable versions. Status constrained; version numbers unique per return. |
| `tax_calculations` | Every engine run, never overwritten. Headline figures denormalised for querying; full results, trace and findings as JSONB. |

### Documents
| Table | Purpose |
| --- | --- |
| `tax_documents` | Metadata and an object-store key. File contents never enter the database. |
| `document_extractions` | One row per extracted value, with confidence, verification state, and the taxpayer's correction kept separately so extractor accuracy can be measured rather than estimated. |

### Filing
| Table | Purpose |
| --- | --- |
| `payments` | Amount, status, processor reference. No card data of any kind. |
| `consents` | Append-only. Stores a hash of the exact text shown — without it, "they agreed to the terms" is an assertion about a document that has since changed. |
| `signatures` | Bound to `signed_content_sha256`. A return altered after signing no longer matches. |
| `efile_submissions` | Carries `channel` so no report can present a simulation as a filing. |
| `efile_acknowledgments` | Carries the acceptance check constraint. |

### Audit and governance
| Table | Purpose |
| --- | --- |
| `audit_logs` | Append-only. No `updated_at` and no update path. |
| `security_events` | Separate from audit: different access patterns, different retention, feeds alerting. |
| `sensitive_data_accesses` | Every staff view of unmasked data, with a mandatory justification. |
| `support_cases` | |
| `rule_set_approvals` | Approval bound to a content hash, so a rule set edited after approval no longer matches. |

## Decisions worth defending

**UUID primary keys.** A sequential return id in a URL tells an attacker what
to try next and tells anyone who sees one how many returns the company has
processed. Object-level authorization is still enforced on every request —
unguessable ids are a speed bump, not an access control — but they remove the
trivial enumeration path.

**`NUMERIC(14,2)` for money.** Exact. A `FLOAT` column would reintroduce at the
storage layer precisely the error the engine exists to avoid.

**JSONB for return input.** It is written and read as a unit, and a version's
input must be reconstructible byte-for-byte after the relational schema
evolves. The cost is that individual fields are not directly queryable, which
is why headline figures are denormalised onto `tax_calculations`.

**Explicit constraint naming conventions.** Without them, autogenerated
migrations produce database-assigned names that differ between environments,
and a later migration that drops a constraint by name fails in exactly one of
them — usually production.

**Selective field encryption, not whole-document.** Encrypting the whole return
would be simpler and would make it opaque to every diagnostic, migration and
analytic query. Most of what is in there — wage amounts, filing status, number
of dependents — is not the sensitive part. The five sensitive paths are
enumerated explicitly rather than discovered by type inspection, so adding a
new sensitive field is a deliberate change a reviewer sees, and the round-trip
test fails if it is missed.

**Two invariants enforced by the database, not just the application.**

```sql
-- efile_acknowledgments
CHECK (status <> 'ACCEPTED' OR (channel = 'LIVE' AND authority_reference IS NOT NULL))
```

```sql
-- migration, when the application role exists
REVOKE UPDATE, DELETE, TRUNCATE ON audit_logs, security_events,
    sensitive_data_accesses, consents, signatures, efile_acknowledgments
    FROM olbostax_app;
GRANT SELECT, INSERT ON (same) TO olbostax_app;
```

Both are verified against a live database. The first rejects a `MOCK`
acceptance and a `LIVE` acceptance with no reference. The second denies
`UPDATE` on `audit_logs` while `INSERT` succeeds and ordinary tables stay
writable.

## Migrations

Alembic, verified to round-trip: upgrade, downgrade to base, upgrade again,
then `alembic check` reports no drift from the models.

Application column types render as their underlying SQL types rather than by
Python import path. A migration that imports application code stops working the
moment that code is refactored away — which is exactly when replaying
migrations from scratch matters.

`compare_type` and `compare_server_default` are on, because type changes are
easy to miss in autogenerate and are the kind that silently truncate data.

The database URL comes from application settings rather than `alembic.ini`, so
a migration cannot be run against a different database from the one the
application uses.
